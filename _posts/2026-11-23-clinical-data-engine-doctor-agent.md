> **架构结论**：医院医生助手不应被设计成“直接连接病历数据库的大模型”。更稳妥的路线是构建两个解耦的核心系统：**Clinical Data Engine（临床数据引擎）**沉淀可信的患者事实，**Doctor Agent**基于受控工具完成临床信息检索、分析编排与辅助表达。前者是可复用的数据基础设施，后者是面向医生工作流的智能应用。
>
> 本文是一份**目标架构与实施方案**，不是已完成临床验证的产品说明。诊疗决策仍由具备资质的临床人员承担，涉及医嘱或病历写入的功能需要额外验证与审批。

此前调研 [Mirobody](https://github.com/thetahealth/mirobody) 时，一个重要发现是：个人健康助手的技术价值并不局限于对话。医疗数据的接入、归一化、纵向组织以及通过 Agent 工具使用数据，才是值得迁移到医院侧的架构思路。但医院有明确的就诊上下文、数据来源、患者授权和责任边界，不能简单把个人 PHR 产品换成医生界面。

## 一、总：为什么选择双层解耦架构

### 1.1 要解决的不是“让医生能和病历聊天”

医院的 HIS、EMR、LIS、PACS 等系统保存了大量患者信息，但现实中仍存在四种断层：

1. **数据断层**：检验、病历、诊断、用药与影像报告分散在不同系统，编码、单位和结构不统一。
2. **时间断层**：医生需要的是患者跨次就诊的变化，而不是孤立的一份报告。
3. **证据断层**：AI 可以生成看似完整的总结，却不一定能指出每个关键事实来自哪份原始记录。
4. **流程断层**：通用聊天界面不理解“当前医生正在查看哪个患者、哪一次就诊、拥有什么操作权限”。

因此，核心目标不是增加一个聊天框，而是让医生在现有工作流中，**更快地获取可核对的患者事实，更安全地使用 AI 辅助分析**。

### 1.2 总体架构

~~~text
                    医生工作站 / EMR / 门诊与住院工作流
                                    │
                         已认证医生 + 当前就诊上下文
                                    │
                  ┌─────────────────▼──────────────────┐
                  │             Doctor Agent            │
                  │ 意图识别 · 任务编排 · 医学知识检索    │
                  │ 工具调用 · 证据核对 · 草稿生成        │
                  └─────────────────┬──────────────────┘
                                    │ 受控工具/API契约
                           鉴权 · 审计 · 版本 · 限流
                                    │
                  ┌─────────────────▼──────────────────┐
                  │        Clinical Data Engine         │
                  │ 采集/解析 → 标准化 → 质量校验        │
                  │ 临床事实存储 · 时间线 · 证据溯源      │
                  └─────────────────┬──────────────────┘
                                    │
                    HIS / EMR / LIS / PACS / 外部报告
                                    │
                       原始数据与来源记录（保留）
~~~

这里的解耦是**业务边界与数据契约解耦**，而非要求首日就拆成大量微服务。初期可以是两个独立模块或服务、一个受控工具网关；稳定后再按负载和团队边界拆分。

| 维度 | Clinical Data Engine | Doctor Agent |
| --- | --- | --- |
| 主要职责 | 维护可信、可查询的临床事实 | 理解医生需求，组合工具完成任务 |
| 核心输入 | 医院原始记录、事件与标准编码 | 医生问题、受控患者上下文、工具结果 |
| 核心输出 | 结构化事实、时间线、证据引用 | 可核对的摘要、分析与待审核草稿 |
| 正确性重点 | 字段、单位、时间、状态、来源准确 | 不越权、不编造、不混淆事实与建议 |
| 迭代节奏 | 稳定、可回放、版本化 | 模型和工作流可快速试验 |
| 系统定位 | 长期数据资产 | 可以替换和扩展的应用层 |

**关键规则：模型不直接访问 HIS/EMR/LIS 数据库，也不凭自然语言中的姓名自行选择患者。**

### 1.3 范围与非目标

首期优先构建**只读型 Doctor Copilot**：患者摘要、时间线、检验趋势、既往诊断与用药核对、报告检索、指南检索。首期不自动诊断、不自主生成正式医嘱、不绕开医生修改病历，也不把向量检索结果当成临床真实数据源。

## 二、分：Clinical Data Engine——临床事实基础设施

### 2.1 数据接入：先解决来源和身份，再解决 AI

推荐采用适配器接入不同医院系统。结构化数据优先使用既有接口、消息或数据交换机制；非结构化报告再交给 OCR、文档解析及抽取模型。

| 来源 | 首期关注的数据 | 接入方式示例 |
| --- | --- | --- |
| HIS / EMR | 患者、就诊、诊断、病历文本、医嘱 | 数据服务 API、HL7 v2、FHIR 适配、受控同步 |
| LIS | 检验项目、数值、单位、参考范围、报告状态 | 接口、消息或变更同步 |
| PACS / RIS | 影像检查索引、结构化/文本报告 | DICOM 元数据、报告接口；首期不要求理解原始影像 |
| 药学及护理系统 | 处方、发药、给药与用药核对记录 | 医院内部业务接口 |
| 患者自带资料 | 外院检验单、体检报告、患者自述 | 文档解析 + 来源标注 + 人工核验 |

这里最容易被忽视的工作是**患者主索引与就诊关联**。必须有可靠的患者身份匹配和 Encounter 关联策略；匹配不确定时进入人工处理队列，不能让模型“猜测是同一个人”。

### 2.2 数据处理流水线

建议将数据处理分为六步：

~~~text
数据采集
  → 原始文档/消息落盘（不可丢失）
  → 解析与结构化抽取（OCR / 规则 / LLM）
  → 术语、单位、时间和状态标准化
  → 规则校验 + 跨源冲突检测 + 低置信度人工复核
  → 临床事实入库 + 溯源索引 + 事件/快照更新
~~~

大模型适合处理**非结构化理解**，但不应承担所有数据处理工作：单位换算、时间排序、数值计算、状态机校验和编码映射应尽量由可测试的规则与程序完成。

**标准化不是把原始数据覆盖掉。** 对每条事实保留“原始值”和“标准化值”，记录使用的词表、规则和抽取模型版本，并支持更正规则后重放处理。

### 2.3 统一临床数据模型

可以参考 HL7 FHIR 的资源语义设计内部 Canonical Model；但**内部使用 FHIR 风格的模型，不等于已经实现完整 FHIR Server**。首期宜明确支持的字段子集与版本，再用适配层对接院内系统。

| 领域 | 推荐实体 | 关键注意点 |
| --- | --- | --- |
| 身份与上下文 | Patient、Encounter | 患者身份、就诊范围、合并与拆分 |
| 病史与诊断 | Condition、Procedure | 问题状态、诊断日期、来源与否定表述 |
| 检验与检查 | Observation、DiagnosticReport | 指标编码、结果值、参考范围、报告状态 |
| 影像与文档 | ImagingStudy、DocumentReference | 报告和原始文档的定位关系 |
| 用药与过敏 | MedicationRequest、MedicationStatement、MedicationAdministration、AllergyIntolerance | 区分开立、患者自述、实际给药与过敏记录 |
| 溯源与审计 | Provenance、AuditEvent（或内部等价模型） | 谁、在何时、基于何来源作了何变更 |

**用药语义特别重要**：存在处方 ≠ 患者已服药；存在发药记录 ≠ 已实际给药；患者自述用药也不等于医院确认的现行处方。Doctor Agent 必须看到这些差异。

在编码层，检验指标可优先评估 LOINC、单位采用 UCUM，诊断及临床术语按院方既有体系与许可条件映射 ICD、SNOMED CT 等；药品编码则要对接本地药品目录。标准之间的映射需有人工维护与版本管理。

### 2.4 每条事实必须回答六个问题

一条检验记录不仅是“肌酐 = 97”，至少还要知道：

- **谁**：属于哪个患者与就诊；
- **是什么**：原始项目名称、标准编码、数值与单位；
- **何时**：采样时间、报告时间、入库时间，避免混用；
- **何种状态**：初步、最终、修正、撤销或待核验；
- **来自哪里**：系统、报告 ID、原文位置或原始消息；
- **如何得到**：抽取方式、归一化规则版本、人工更改记录。

下面是仅用于说明接口结构的**虚构数据**，不代表对任何真实患者的判断：

~~~json
{
  "observation_id": "obs_demo_001",
  "code": {"system": "LOINC", "value": "2160-0"},
  "display": "血肌酐",
  "value": 97,
  "unit": "umol/L",
  "effective_at": "2026-10-20T09:20:00+08:00",
  "status": "final",
  "source": {
    "system": "LIS",
    "report_id": "lab_demo_001",
    "item_ref": "item-5"
  },
  "verification": "source_verified",
  "normalization_version": "rules-2026.11",
  "snapshot_id": "snap_demo_01"
}
~~~

若同一指标出现冲突值，应保留多份来源和修订关系，依据报告状态、时间与院内规则处理；**绝不简单让 LLM 挑选“更像正确答案”的数值**。

### 2.5 存储与查询：结构化数据才是事实源

建议将数据职责拆开：

- **原始层**：加密保存原始报告、消息或文件，支持溯源和重放。
- **事实层**：关系数据库保存患者、就诊、标准化观察值、诊断、用药状态和版本关系；这是临床事实的主查询来源。
- **检索层**：全文检索服务检索病历段落、报告，向量索引只用于语义召回，结果必须关联原始文档与患者授权。
- **审计层**：保留数据修改、医生访问与工具调用记录，按医院策略保留与脱敏。

PostgreSQL 可承担首期关系型事实存储；对象存储保存原文，队列与 Worker 处理异步抽取。是否增加 OpenSearch、pgvector 等取决于实际数据量和召回需求，**不必为了 Agent 而先引入复杂基础设施**。

### 2.6 数据引擎对外暴露的是“受控能力”，不是整张表

推荐把数据引擎的能力封装为稳定服务，例如：

| 能力 | 返回内容 | 边界 |
| --- | --- | --- |
| get_patient_summary | 患者基础情况及重要事件 | 限定当前授权上下文 |
| get_patient_timeline | 跨就诊事件时间线 | 可过滤时间、事件类型 |
| query_lab_results | 指定检验指标的结构化记录 | 保留单位、参考区间、状态和来源 |
| compare_lab_trends | 趋势与确定性统计结果 | 数值运算由程序执行 |
| get_medication_history | 处方、自述、发药、给药等记录 | 不将不同状态合并为“正在服药” |
| get_allergies | 过敏与不耐受信息 | 区分已确认、待确认、否认与未知 |
| get_source_document | 有权限的原始证据片段 | 返回最小必要文本、页码和定位 |

底层可以是 REST/gRPC；对 Doctor Agent 再包装成 MCP 或 Function Calling 工具。**MCP 是工具协议选择，不是医疗数据模型，也不能替代鉴权。**

## 三、分：Doctor Agent——围绕医生工作流的智能编排层

### 3.1 Agent 的职责边界

Doctor Agent 应当负责：

1. 识别医生提出的任务类型；
2. 根据当前患者与就诊上下文规划信息需求；
3. 调用患者数据工具、医学知识工具与确定性计算工具；
4. 合并证据，识别缺失、过期或相互冲突的信息；
5. 生成便于医生审阅的结构化结论、摘要或草稿。

Agent **不负责**自行创造患者事实、擅自跨患者检索、直接更改临床事实库，或将生成的医学建议包装为已经确认的医嘱。

### 3.2 采用 Tool-first，而不是 Prompt-first

一次典型工作流可表示为：

~~~text
医生问题：「看一下这位患者近一年的肾功能趋势和用药情况」
  │
  ├─ 工作站传入受控患者/就诊上下文
  ├─ Agent 选择 query_lab_results、compare_lab_trends
  ├─ Agent 选择 get_medication_history
  ├─ 数据引擎执行授权、查询与数值计算
  ├─ Agent 汇总结果，标记缺失/冲突/不确定项
  └─ 返回：趋势摘要 + 数据表 + 用药状态 + 来源链接
                         ↓
                    医生审阅与判断
~~~

此工作流中，“近一年”的时间窗口可以由 Agent 解析，但具体数值、趋势计算和证据链接应来自工具输出；关键结论应能定位到具体观察值、报告或记录。

### 3.3 把工具分成三组

**患者事实工具**：患者摘要、时间线、检验查询、诊断史、用药史、过敏史、报告检索。由 Clinical Data Engine 提供。

**医学知识工具**：检索临床指南、院内诊疗规范、药品说明书、医学文献。必须带来源、发布日期、版本或适用范围，且不得冒充患者本人事实。

**确定性计算与草稿工具**：临床评分、单位换算、规则校验、病历草稿生成等。评分的输入字段、公式版本和计算结果都应可检查；生成草稿须明确“待医生确认”。

这三类工具分开，可以避免把“指南推荐”“患者事实”“模型推测”混成一段无法核验的文字。

### 3.4 模型服务可以替换，临床数据不能跟着重做

建议将模型能力抽象为以下可配置服务：

| 模型/能力 | 适用任务 | 设计原则 |
| --- | --- | --- |
| OCR / 视觉文档模型 | 扫描件、表格、报告解析 | 低置信度进入复核，保留原文 |
| 信息抽取模型 | 病历字段与事实候选抽取 | 结果经规则、状态和来源校验后入库 |
| 对话/推理 LLM | 意图理解、工具规划、摘要与草稿 | 通过工具访问数据，不直接获得数据库权限 |
| Embedding / Reranker | 语义检索和文本重排 | 只负责召回，不决定临床事实真伪 |
| 规则与计算服务 | 单位换算、趋势统计、临床评分 | 可测试、版本化、确定性优先 |

部署可采用医院内网模型、专有环境模型服务或经院方批准的外部服务。**是否允许敏感数据离开院内边界是治理决策，不应成为 Agent 自行选择模型供应商的运行时行为。**

### 3.5 面向医生设计，不复制患者聊天产品

更合适的医生端界面不是单独的聊天 App，而是嵌入工作站的**患者上下文侧栏**。建议首期提供四个入口：

- **接诊前速览**：既往诊断、重要手术、过敏和近期关键事件；
- **检验趋势**：指标曲线、数值表、参考范围与原报告跳转；
- **跨文档问答**：回答问题同时列出证据及冲突信息；
- **病历摘要草稿**：形成可编辑内容，医生确认后才进入既有工作流。

在 UI 上，**事实、推断、建议、待确认信息需要明确区分**。若证据不足，应展示“不足以确认”，而不是强行给出肯定答案。

## 四、分：两层如何协作，以及医院必须补齐的安全能力

### 4.1 以 Clinical Context + Tool Contract 对接

医生打开患者时，由医院工作站或后端建立授权会话；Tool Gateway 绑定用户身份、科室、患者、就诊和用途。LLM 只能提交诸如“检索最近 12 个月的检验”这样的工具参数，**不能通过自由填写 patient_id 切换患者**。

接口可按下面的逻辑设计：

~~~text
EMR / 工作站
  └─ Backend 创建 clinical_context
      ├─ clinician_id（认证身份）
      ├─ patient_id / encounter_id（服务端绑定）
      ├─ purpose_of_use / scopes
      └─ context_expiry
           ↓
Doctor Agent → Tool Gateway → Policy Check → Clinical Data Engine
                                         ↓
                             结构化事实 + 证据引用 + 快照版本
~~~

示意性工具请求：

~~~json
{
  "tool": "query_lab_results",
  "arguments": {
    "codes": ["2160-0"],
    "lookback_months": 12,
    "include_provenance": true
  }
}
~~~

**注意**：请求中不暴露可由模型自行填写的 patient_id。服务端从受信任的 clinical_context 解析患者与就诊，并重新执行授权校验。工具响应应包括 snapshot_id、来源标识、可定位的证据及必要的不确定性字段，避免多轮对话使用相互矛盾的数据版本。

### 4.2 安全、权限与审计是架构的一部分

医院侧至少需要以下控制：

- **身份与授权**：对接院内 SSO/IAM，结合 RBAC、ABAC、就诊关系、用途和最小权限，服务端逐次校验。
- **患者上下文隔离**：会话切换、权限撤销或过期时，立即清除旧患者上下文和相关缓存。
- **原始数据保护**：传输与静态加密、密钥管理、访问审计、存储隔离和受控导出；日志避免记录不必要的敏感全文。
- **提示注入防护**：病历、报告、网页和检索片段均视为不可信内容，不能借其文字修改工具权限、系统指令或患者身份。
- **证据与版本**：追踪原始报告、抽取/标准化规则、模型版本、工具输出、医生修订及最终使用状态。
- **高风险动作隔离**：病历写入、医嘱、处方和检查申请必须通过明确的审批、确认、业务校验及院内事务接口，不由通用 Agent 隐式执行。

遵循当地适用的数据保护、医疗软件和医院信息安全要求，并在上线前完成法务、信息安全、临床治理评估。**私有化部署本身并不自动意味着满足合规要求。**

### 4.3 失败场景应提前定义

| 失败或边界场景 | 系统应如何处理 |
| --- | --- |
| 上游 LIS 暂不可用 | 返回数据更新时间和不完整标记，不假装已获取最新结果 |
| 两份报告数值冲突 | 展示来源与状态冲突，触发核验策略 |
| 患者身份关联不确定 | 暂停合并，进入人工核对 |
| 旧检验单位映射不确定 | 保留原始单位，不做无依据换算 |
| 指南知识库过期 | 显示版本日期并提示需核对 |
| LLM 超时或故障 | 医生仍能访问确定性数据查询和原始报告 |
| 上下文过期或越权 | 拒绝工具调用，不返回敏感数据 |
| 生成摘要没有证据 | 不呈现为已核实临床事实 |

技术上的可靠性与临床上的安全性不是一回事。高可用、低延迟只能说明服务运行稳定，**不能替代临床事实准确性与工作流安全性的验证**。

## 五、总：部署方案、实施路径与验收标准

### 5.1 推荐的最小可行部署

对于单院区试点，不建议先搭建大规模多 Agent 平台。可以优先采用：

~~~text
医院网络 / 受控专有环境
├─ 数据接入适配器（HIS / EMR / LIS）
├─ 解析 Worker（规则、OCR、必要时调用抽取模型）
├─ Clinical Data API
│  ├─ PostgreSQL：患者/就诊/临床事实/溯源
│  ├─ 对象存储：原始报告与附件
│  └─ 可选全文检索/向量检索
├─ Tool Gateway + 授权策略 + 审计
├─ Doctor Agent Orchestrator + Model Gateway
│  └─ 院内模型或受批准的专有模型服务
└─ 医生工作站侧栏 / EMR 集成
~~~

解析 Worker 和 Agent 推理应分开扩缩容：批量报告抽取偏吞吐，医生交互偏低延迟。CPU/内存首先按数据规模与并发测算；GPU 取决于 OCR、抽取模型和 LLM 是否本地运行，**不能直接把个人版 Mirobody 的硬件推荐当作医院生产容量规划**。

### 5.2 分阶段落地路线

| 阶段 | 建设目标 | 核心交付物 | 验收重点 |
| --- | --- | --- | --- |
| P0：场景与数据盘点 | 锁定科室、任务、接口和责任边界 | 数据字典、权限矩阵、风险清单、评测集 | 确认哪些来源可用、哪些动作禁止 |
| P1：临床数据引擎 MVP | 打通患者、就诊、检验、报告及基础用药记录 | 适配器、标准化流水线、事实 API、溯源链 | 结构化准确性、修订回放、患者隔离 |
| P2：只读 Doctor Copilot | 门诊摘要、检验趋势、跨报告检索、用药核对 | Tool Gateway、Agent 工作流、医生侧栏 | 证据覆盖、越权拦截、医生可用性 |
| P3：工作流增强 | 病历草稿、院内指南、临床评分 | 草稿审核流程、知识版本管理、质量监控 | 医生审核、版本治理、回退机制 |
| P4：有条件扩展 | 评估写入与决策支持场景 | 分级审批、院内业务接口、独立临床验证 | 未通过安全评审不开放自动执行 |

建议选择**一个科室、两个到三个高频只读任务**做端到端闭环，再扩充病种和数据源。架构是否成功，首先看医生能否从结论一键追溯到原始证据，而不是 Agent 能调用多少个工具。

### 5.3 如何衡量成效

至少建立四组指标，并以试点前的人工基线作对照：

| 评价维度 | 需要持续测量的指标 |
| --- | --- |
| 数据质量 | 字段抽取准确率、单位标准化正确率、患者/就诊匹配错误、冲突识别率 |
| 证据可信度 | 关键事实证据覆盖率、引用定位正确率、陈旧数据提示率、无来源断言数量 |
| 安全与鲁棒性 | 越权访问阻断、上下文隔离、提示注入测试、敏感数据外泄、故障降级 |
| 临床工作流价值 | 医生完成任务耗时、核对成本、修改率、主观可用性与安全事件 |

通过去标识化或合成测试数据建立医生标注的评测集，并覆盖冲突、纠错、缺失、跨患者、时间错乱、处方与给药不一致等难例。**高风险事实错误应设为阻断发布的安全门槛**，不能仅用通用 LLM 问答得分作为上线依据。

### 5.4 Mirobody 值得借鉴什么、不宜照搬什么

从 [Mirobody 开源项目](https://github.com/thetahealth/mirobody) 中，可以重点研究：

- **医疗数据标准化引擎**：原始值与归一化值分离、术语和单位处理；
- **纵向健康档案**：把离散报告组织成跨时间的可查询事实；
- **Agent / MCP 工具模式**：将数据访问能力封装为受控工具；
- **本地模型与数据处理分工**：让 LLM 负责理解和编排，确定性代码负责计算与校验。

但医院侧必须重新设计的部分也很明确：HIS/EMR/LIS/PACS 的正式集成、患者主索引、Encounter 语义、复杂用药状态、医生级授权、审计、临床质量验证和院内写入工作流。具体代码是否能够复用，还要单独审核其许可证、依赖、安全性和维护状态。

### 5.5 最终结论

**长期沉淀的是 Clinical Data Engine，持续演进的是 Doctor Agent。**

第一层把医院的原始数据变成**可追溯、可计算、可授权查询的临床事实**；第二层把这些事实和经过版本管理的医学知识转化为**医生可以审阅、核对和使用的辅助工作结果**。两者之间依靠稳定的 Tool Contract、可信患者上下文和统一审计连接。

这条路线的价值不止是做出一个医生聊天助手，而是建设一套可以服务于门诊、住院、随访与其他临床应用的 AI 数据与工具基础设施。真正的优先级是：**先把事实做准、把权限守住、把证据连通，再逐步增加智能化程度。**
